# 日本法令の相互参照ルール仕様書
### ― 解析ソフトウェア設計のための実務リファレンス ―

本書は、日本の法令(法律・政令・省令・条例等)の条文に現れる「相互参照表現」を機械的に解析するために、参照パターンを網羅的に整理したものである。法制執務(法令の立案・作成に関する実務慣行)のルールに基づく。

---

## 0. 前提知識:条文の階層構造

参照を解析するには、まず「今どこを読んでいるか(位置)」をアプリ内部で座標として持てる必要がある。日本の法令の階層は以下の通り。

```
法令
└ 編 (Part)
  └ 章 (Chapter)
    └ 節 (Section)
      └ 款 (Subsection)
        └ 目 (Division)
          └ 条 (Article)      … 第◯条、枝番号は 第◯条の2
            └ 項 (Paragraph)  … 枝番号なし。第1項は番号非表示、2項以降"２""３"…
              └ 号 (Item)     … 漢数字 "一""二""三"…、枝番号は 一の二 等
                └ 号の細分1 (Subitem1) … イ、ロ、ハ…
                  └ 号の細分2 (Subitem2) … (1)(2)(3)…
                    └ 号の細分3 (Subitem3) … (i)(ii)(iii) ※稀
```

**設計上の要点**

| 単位 | 番号表記 | 枝番号(挿入時の追い番) | 備考 |
|---|---|---|---|
| 条 (Article) | 第◯条 | あり(第◯条の2、の3…) | 独立した1条としてカウントされる |
| 項 (Paragraph) | (1項は無表示)、2項以降 算用数字 | **なし** | 挿入時は後続項をすべて繰り下げる必要がある |
| 号 (Item) | 漢数字(一、二、三…) | あり(一の二 等) | |
| 号の細分1 | イロハ | なし | |
| 号の細分2 | (1)(2)(3) | なし | |

条・号に枝番号があるのは、既存条文の番号を変えずに済ませ、他法令からの引用リンクを壊さないため。項には枝番号がない点は解析上ハマりやすい罠(「項が増える改正」では必ず既存項の番号がズレる)。

このほか、条文本体(本則)とは別に **附則**(ふそく)、**別表**、**様式** という構造があり、これらも独自の参照対象になる(§6)。

## 1. 定義参照(「以下○○という」型)

### 1.1 パターン

| 表現 | 意味 |
|---|---|
| 〜(以下「A」という。) | 直前の語句・概念に略称Aを与える。以後その適用範囲内でAはこの定義に従う |
| 〜(以下単に「A」という。) | 同上。「単に」は他に紛らわしい略称がある場合の使い分け |
| 〜以下同じ。 | 直前で示した意味・解釈を、指定範囲の以降すべての箇所で同様に適用する宣言(略称の定義とは限らず、語の意味の指定にも使う) |
| この条において「A」とは、…をいう。 | その条の中だけで有効なローカル定義 |
| この章において「A」とは、…をいう。 | 章単位のスコープを持つ定義 |
| この法律において「A」とは、…をいう。 | 法令全体に及ぶグローバル定義(通常は第2条などの「定義」条に集約) |

### 1.2 スコープ(有効範囲)の決定規則

定義の効力範囲は **定義が置かれた条文の見出し・文言に明示される** ため、解析時は次の優先順位で有効範囲を確定する。

1. 「この法律において」「この政令において」→ 法令全体
2. 「この章において」「この節において」→ その章・節の内部のみ
3. 「この条において」→ その条のみ
4. 明示がなく単に「(以下「A」という。)」だけの場合 → **その語が出現した条文以降、法令末尾まで**が原則(ただし「附則」に入ると効力が切れる場合があるので注意)
5. 「以下同じ。」は直前の定義・限定を、指定された範囲(多くは「この条において」等とセットで使われる)に適用範囲を広げる/確認する働き

### 1.3 実装のための正規表現例

```regex
# 略称定義の検出
(?:以下)?(?:単に)?「(?P<alias>[^」]+)」という。

# スコープ宣言の検出
この(?P<scope>法律|政令|省令|規則|条例|章|節|款|条|項)において、?「(?P<term>[^」]+)」とは、(?P<definition>.+?)をいう。

# 「以下同じ」検出
以下同じ。
```

**解析アルゴリズム**:定義を見つけたら `{alias: alias, definition_span: 定義された条文位置, scope: スコープ, valid_from: 出現位置}` のレコードをシンボルテーブルに登録し、以後の本文中に同じ文字列(カギカッコなし)が出現するたびに、有効範囲内であればそのレコードにリンクを張る。

## 2. 相対位置参照(前・次・同・当該)

法令改正で条番号がズレても本文を書き換えずに済むよう、位置関係だけで参照する表現群。**「今どの条・項・号を読んでいるか」という座標(カーソル)を持たないと解決できない**、パーサ設計上もっとも重要なグループ。

### 2.1 基本語彙表

| 語 | 意味 | 参照範囲の粒度 |
|---|---|---|
| 前条 | 直前の条(1つ前) | 条 |
| 次条 | 直後の条(1つ後) | 条 |
| 前項 | 直前の項(1つ前、同一条内) | 項 |
| 次項 | 直後の項(1つ後、同一条内) | 項 |
| 前号 | 直前の号(1つ前、同一項内) | 号 |
| 次号 | 直後の号(1つ後、同一項内) | 号 |
| 同条 | 直前に言及した条と同じ条 | 条 |
| 同項 | 直前に言及した項と同じ項 | 項 |
| 同号 | 直前に言及した号と同じ号 | 号 |
| 当該 | 直前に出てきた対象そのもの(代名詞的) | 任意の名詞句 |
| 本条 | 今読んでいるこの条(自条参照。契約書で多用、法令では稀) | 条 |
| 本項 | 今読んでいるこの項 | 項 |

### 2.2 範囲指定(前○条・前各項など)

| 表現 | 意味 |
|---|---|
| 前二条 | 直前の2つの条(現在条の1つ前・2つ前) |
| 前三項 | 直前の3つの項 |
| 前各項 | 同一条内で、現在の項より前にあるすべての項 |
| 前各号 | 同一項内で、現在の号より前にあるすべての号 |
| 次二項 | 直後の2つの項 |

**「前各項」の解決例**:第3条第5項に「前各項」とあれば → 第3条第1項〜第4項全部を指す。

### 2.3 前段・後段、本文・ただし書

1つの文が意味的に前後半に分かれる場合の参照。

| 語 | 意味 |
|---|---|
| 前段 | ひとつの文の前半部分(読点でなく、内容的な区切りで分割) |
| 後段 | ひとつの文の後半部分 |
| 本文 | 「ただし、」以下を除いた原則規定部分 |
| ただし書 | 「ただし、」から始まる例外規定部分 |

例:「第9条ただし書に規定する行為については、この限りでない。」→ 第9条の「ただし、…」の部分だけを指す。

### 2.4 「前項の場合」と「前項に規定する場合」の違い(重要な落とし穴)

- **「前項の場合」**:前項の内容**全体**を受けて、それに情報を追加する。
- **「前項に規定する場合」**:前項の中の**一部**(「…の場合」「…のとき」といった仮定条件部分だけ)を受けて、それに情報を追加する。

この2つは字面が似ているが指す範囲が異なるため、単純な文字列一致で「前項」を検出するだけでは不十分。「前項の」の直後の名詞(「場合」か、それ以外の名詞か)まで見て、意味的にどの部分を受けているかを判定するロジックが必要。

### 2.5 解決アルゴリズム(擬似コード)

```
現在位置 = (法令ID, 条番号, 項番号, 号番号)  # カーソル

def resolve_relative_ref(token, cursor):
    if token == "前条":
        return cursor.article - 1  # 枝番号を考慮した「1つ前の条」
    if token == "次条":
        return cursor.article + 1
    if token == "前項":
        return (cursor.article, cursor.paragraph - 1)
    if token.match(r"前([一二三四五六七八九十]+)条"):
        n = kanji_to_int(token)
        return range(cursor.article - n, cursor.article)  # n個前まで全部
    if token == "前各項":
        return range(1, cursor.paragraph)  # 同条内、1項からcursor直前まで
    if token == "同条":
        return last_referenced_article  # 直近で言及された条を記憶しておく必要あり
    if token == "当該":
        return last_referenced_entity   # 直近の名詞句を指す(要:直近アンカーの管理)
    ...
```

実装上のポイントは **「直近に言及した対象」を常にスタックのように保持しておくこと**。「同条」「同項」「当該」はこの履歴参照に依存するため、単純な現在位置だけでは解決できない。

## 3. 直接参照(条文番号を明示するもの)

### 3.1 基本形

| 表現 | 意味 |
|---|---|
| 第10条 | 条番号を直接指定 |
| 第10条第2項 | 条+項を指定 |
| 第10条第2項第3号 | 条+項+号を指定 |
| 第10条の2 | 枝番号付きの条 |
| 第10条第2項第3号イ | 号の細分まで指定 |

### 3.2 範囲・除外・複数指定

| 表現 | 意味 |
|---|---|
| 第10条から第15条まで | 第10条〜第15条の範囲すべて |
| 第10条及び第12条 | 第10条と第12条の2つ(並列、連続しない) |
| 第10条(第3項を除く。) | 第10条全体からその第3項だけを除外 |
| 第10条第1項から第3項まで | 同一条内の項の範囲 |
| 第1号から第3号まで | 号の範囲 |

### 3.3 他法令への参照(外部参照)

| 表現 | 意味 |
|---|---|
| 民法(明治二十九年法律第八十九号)第90条 | 法令名+法令番号+条番号で他法令を一意に特定 |
| 同法第10条 | 直前に言及した(外部)法令の第10条 |
| この法律 | 参照している法令自身を指す(自己参照) |

外部参照は初出時に必ず「法令名(元号+年+法律番号)」の形でフルネームが書かれ、以後は「同法」で省略されるのが通例。パーサは初出フルネームを法令IDに正規化してテーブルに保持し、「同法」をそのIDへのポインタとして解決する。

### 3.4 実装のための正規表現例

```regex
# 条項号の直接参照(枝番号・細分号対応)
第(?P<article>[〇一二三四五六七八九十百千0-9]+)条(?:の(?P<article_sub>[〇一二三四五六七八九十0-9]+))?
(?:第(?P<paragraph>[0-9]+)項)?
(?:第(?P<item>[〇一二三四五六七八九十0-9]+)号(?:の(?P<item_sub>[〇一二三四五六七八九十0-9]+))?)?

# 範囲参照
第(?P<from>[0-9]+)条から第(?P<to>[0-9]+)条まで

# 除外
第(?P<article>[0-9]+)条\(第(?P<excluded>[0-9]+)項を除く。\)

# 他法令名+法令番号
(?P<law_name>[^\s(（]+)(?:（|\()(?P<era>明治|大正|昭和|平成|令和)(?P<year>[〇一二三四五六七八九十0-9]+)年(?P<type>法律|政令|省令|規則|条例)第(?P<number>[〇一二三四五六七八九十0-9]+)号(?:）|\))
```

**注意**:条文中の数字表記は「漢数字(一、二、三…)」と「算用数字(1、2、3…)」が法令によって混在するため、漢数字↔算用数字の相互変換関数(`kanji_to_int` / `int_to_kanji`)を必ず用意すること。

## 4. 準用・読み替え・適用(応用参照)

これは単なる「参照」ではなく、**他の条文のルールを借りてきて、必要なら語句を差し替えたうえで当てはめる**という、参照+変換のパターン。パーサ設計上は「参照エッジ」に加えて「置換ルール」を持つグラフ構造で表現するのが適切。

### 4.1 用語の使い分け

| 用語 | 意味 |
|---|---|
| **適用する** | ある規定を、本来その規定が対象としている事項にそのまま当てはめる |
| **準用する** | ある規定を、本来の対象ではないが性質が似ている別の事項に、必要な修正を加えて当てはめる |
| **例による** | 準用に近い。別の制度の取扱い全体を借りてくる、より緩やかな表現 |

### 4.2 準用+読み替えの定型文パターン

```
第◯条の規定は、△△について準用する。この場合において、同条中「A」とあるのは、「B」と読み替えるものとする。
```

これは以下の2つの操作を意味する:
1. 「準用元」条文(第◯条)のテキストを、「準用先」の対象(△△)に丸ごとコピーして適用する
2. その際、コピーしたテキスト中の文字列「A」をすべて「B」に置換してから適用する(読み替え)

### 4.3 読み替えのバリエーション

| 表現 | 構造 |
|---|---|
| 準用読替 | 「〜について準用する。この場合において、〜とあるのは、〜と読み替えるものとする。」 |
| 読替適用 | 「〜の適用については、第◯条中「〜」とあるのは、「〜」とする。」(準用ではなく直接適用の場合の読み替え) |
| 複数箇所読み替え | 「同条中「A」とあり、及び「B」とあるのは、「C」と読み替える。」(複数の異なる箇所を同じ語に置換) |
| 附則での読み替え | 経過措置として、施行日をまたぐ適用について読み替える場合。附則に別建てで書かれることが多い |

### 4.4 データ構造の提案

```json
{
  "type": "quasi_application",
  "source_ref": {"law": "獣医療法", "article": 5},
  "target_scope": "農林水産省令で定める診療用機器その他の物品を所有し、又は借り受けてこれを使用する往診診療者等",
  "substitutions": [
    {"from": "診療施設", "to": "診療用機器等"},
    {"from": "構造設備、医薬品その他の物品の管理及び飼育動物の収容", "to": "診療用機器等"}
  ]
}
```

このように準用条文をグラフの「エッジ」として持たせ、置換ルールを属性として保持すれば、「実質的に適用される条文の全文」をプログラムで動的に再構成できる(準用先条文を読むときに元の条文＋置換を適用してレンダリングする、という応用が可能になる)。

## 5. 法的効果を伴う指示語(みなす・推定する)

厳密には「参照」ではないが、条文間の関係を解析するうえで併せて認識しておくべき定型語。

| 語 | 効果 | 反証の可否 |
|---|---|---|
| **みなす** | 本来は異なるものを法律上同一のものとして強制的に扱う(法的擬制) | 反証不可(絶対的) |
| **推定する** | 反対の証拠がない限り、一応そのように扱う | 反証可能(相対的) |

パーサでは、条文に「みなす」「推定する」が出現する箇所を **法的効力の強さが異なる規定** としてタグ付けしておくと、後段の意味解析(この規定は反証で覆るか等)に活用できる。

```regex
とみなす。
と推定する。
```

## 6. 別表・様式・附則への参照

本則(条文本体)以外の構造物への参照。

| 表現 | 意味 |
|---|---|
| 別表第1 | 法令末尾に添付された表(第1番目)への参照 |
| 別表第1(第10条関係) | 別表がどの条文に対応するかを示す注記(別表側に付く) |
| 様式第2号 | 申請書等の書式(様式)への参照 |
| 附則第3条 | 本則とは別に定められる、施行期日・経過措置等を定めた「附則」内の条文 |
| 附則第2項 | 附則内の項(附則は本則と独立した条項体系を持つことが多い) |

**設計上の注意**:附則は本則とは別の条文体系(第1条から独立してカウントされる)を持つことが多いため、パーサの「現在位置」座標には `is_appendix: bool` のようなフラグを持たせ、本則の条番号と混同しないようにする必要がある。

## 7. 列挙の論理接続(参照範囲の境界を左右する)

号の並びなどを参照するとき、「どこからどこまでが1つのまとまりか」を正しく区切るために必須の知識。

| 語 | 意味 | 英語対応 |
|---|---|---|
| 又は | 同じ階層の選択肢を並べる | or(フラット) |
| 若しくは | 選択肢が入れ子(階層)になっている場合、下位階層の選択を示す | or(ネスト) |
| 及び | 同じ階層の並列(かつ)をつなぐ | and(フラット) |
| 並びに | 並列が入れ子になっている場合、上位階層の並列を示す | and(ネスト) |
| その他 | 前後が並列関係(対等)にある場合に使う | (等位接続) |
| その他の | 直前の語句が、直後のより広い概念の**例示の一部**であることを示す | (包含関係) |

**「その他」と「その他の」の違い**は、号の参照範囲・包含関係を解析するときに重要:「A、B その他のC」は「A、Bを含むCという広い概念」を意味し、「A、B その他C」は「A、B、C」の3つが並列であることを意味する。

パーサでこの区別を誤ると、「ある号が別の号の下位概念に含まれるかどうか」の判定を誤るため、号の入れ子構造をASTで表現する際はこの接続語の種類をノード属性として保持することを推奨する。

## 8. 機械可読データソース:法令標準XMLスキーマ(e-Gov)

自前で正規表現パーサを一から作る前に、**デジタル庁が提供する「法令標準XMLスキーマ」に準拠したXMLデータ(e-Gov法令API)を利用する**ことを強く推奨する。条・項・号の階層がすでに構造化タグとして与えられているため、位置座標の管理コストが大幅に下がる。

### 8.1 主要な要素階層

```
Law
└ LawBody
  ├ MainProvision                 … 本則
  │ └ Article (Num="1", Num="1_2"…)   … 条(枝番号は "1_2" のようにアンダースコアで表現)
  │   ├ ArticleTitle              … 「第一条」の見出し文字列
  │   ├ ArticleCaption            … 条見出し(例:「(目的)」)
  │   └ Paragraph (Num="1","2"…)  … 項
  │     ├ ParagraphNum
  │     ├ ParagraphSentence
  │     └ Item (Num="1","2"…)     … 号
  │       ├ ItemTitle
  │       ├ ItemSentence
  │       └ Subitem1              … イロハ
  │         └ Subitem2            … (1)(2)(3)
  │           └ Subitem3          … (i)(ii)(iii)
  ├ SupplProvision                … 附則(本則と独立したArticle体系を持つ)
  └ AppdxTable / AppdxStyle       … 別表・様式
```

- 各要素には `Delete="true"` のような属性が付き、削除された(欠番になった)条項号を判別できる。
- 条の `Num` 属性は枝番号を `1_2`(=第1条の2)のようにアンダースコア表記するため、パース時は `_` をセパレータとして分解すればよい。

### 8.2 API利用例

```
# 条文取得(法令ID指定)
https://laws.e-gov.go.jp/api/1/articles;lawId=405AC0000000088;article=1

# 条+項を指定
https://laws.e-gov.go.jp/api/1/articles;lawId=129AC0000000089;article=1;paragraph=2
```

XMLをパースして `Sentence` 要素のテキストを取り出すだけでなく、`Article/@Num` や `Paragraph/@Num` を使えば「現在位置」の座標管理がXML構造からそのまま得られる。相対参照(前条・前項など)の解決も、この構造化データ上でインデックス演算するだけで済むため、正規表現による本文パースより堅牢になる。

参考実装として、Python製の法令XMLパーサ `ja-law-parser` が公開されている(OSS)。

## 9. 解析パイプライン設計の提案

以上を踏まえた、解析ソフトウェア全体のパイプライン案:

```
1. 取り込み
   e-Gov法令API から法令標準XMLを取得(可能な限りプレーンテキストではなくXMLを使う)

2. 構造化
   XML → 内部AST(法令 > 編/章/節 > 条 > 項 > 号 > 号の細分)
   各ノードに一意な座標 (law_id, article, article_sub, paragraph, item, item_sub) を付与

3. シンボルテーブル構築(§1)
   「以下「A」という」「この法律において」等を全文スキャンし、
   {略称 → 定義本体, 有効スコープ, 出現座標} を登録

4. 参照抽出(トークナイズ)
   条文本文を走査し、以下の正規表現群でヒットした箇所をすべて「参照候補トークン」として抽出:
     - 相対参照語彙(§2): 前条/次条/前項/次項/前号/次号/同条/同項/同号/当該/前段/後段/本文/ただし書/前各項/前各号/前二条 等
     - 直接参照(§3): 第◯条第◯項第◯号 のフルパターン、範囲・除外パターン
     - 外部法令参照(§3.3): 法令名+法令番号のフルネーム、および「同法」

5. 参照解決
   各トークンの種類に応じて解決:
     - 相対参照 → 現在座標からのオフセット計算(§2.5のアルゴリズム)
     - 直接参照 → 座標を直接構築、法令内AST上のノードに解決
     - 外部参照 → 法令名テーブルを引いて対象法令IDに解決、その後は同法令内で上記と同じ処理
     - 「同条」「同項」「当該」 → 直近参照スタックを参照して解決(履歴依存)

6. 準用・読み替えの構造化(§4)
   「準用する」「読み替える」を検出したら、通常の参照エッジとは別に
   {source, target, substitutions[]} の準用エッジとして登録

7. 出力・活用
   - 条文間の参照グラフ(有向グラフ)を構築 → 影響範囲分析(この条を改正すると影響する条文の洗い出し)に利用
   - 準用エッジを辿って「実際に適用される条文の実質テキスト」を動的合成(読み替え反映済み)
   - 定義シンボルテーブルを使い、本文中の用語にはすべて定義箇所へのリンクを自動付与
```

### 9.1 テストすべき代表的な落とし穴(エッジケース)

- 「前項」と「前項に規定する場合」の違い(§2.4) — 全体参照か部分参照かの判定
- 「その他」と「その他の」(§7) — 並列か包含かで号の階層構造の解釈が変わる
- 項には枝番号がない(§0) — 「項が追加された改正」では必ず後続項の番号がズレるので、施行日ごとにバージョン管理が必要
- 「同条」「同項」「当該」は直近文脈依存 — 単純な現在位置だけでは解決できない、履歴スタックが必須
- 附則は独立した条番号体系を持つ — 本則の条番号と衝突させない
- 漢数字/算用数字の混在 — 号は漢数字、項は算用数字が原則だが、法令(特に古い法令や条例)によって表記揺れがある
- 枝番号の表記揺れ — 「第10条の2」の「の2」は漢数字/算用数字どちらの場合もある
